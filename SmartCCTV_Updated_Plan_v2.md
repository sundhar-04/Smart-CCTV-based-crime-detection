# SmartCCTV / Meridian — Updated Integration Plan (v2)

**Supersedes:** UI sections of `SmartCCTV_Software_Design_Document.md` (v1 §9, screens S1–S11). Backend/model sections of v1 (§3–§8, §10–§13) still apply and are referenced, not repeated.
**Companion file:** `AGENT_BUILD_SPEC_v2.md` — build instructions for an AI coding agent.

---

## 1. What changed and why this plan exists

You already have two separate things that were never connected:

1. **The real pipeline** (from the earlier build): YOLO detection cascade, ByteTrack, the risk engine, alert budget, evidence/hash-chain, tamper monitor — Python, tested, produces real alerts from real video when zones are configured correctly.
2. **`Meridian___Surveillance_Operations_Platform.html`**: a single-file React app (React 18 + htm + Chart.js via CDN, no build step) that is a **complete, polished frontend mockup** — 11 pages, role-based nav, settings tabs, incident investigation modal, command palette. It already models almost the exact domain concepts from the SDD (risk engine defaults, signal types, permissions, retention, tamper kinds all appear in its source).

**The catch, confirmed by reading the source:** Meridian has **zero `fetch()` calls**. Every number, alert, camera feed, and detection is generated by a seeded random-number generator (`seededRandom`, `pick(INCIDENT_TYPES)`, etc.) running entirely in the browser. `VideoAnalysisPage` does not analyze the uploaded video at all — it plays the file locally and spawns fake detections on a timer, regardless of video content. **This is why "upload video → get alerts" felt broken: nothing was ever running your model.**

This plan's job: **keep Meridian as the UI** (it's good work, matches the domain model closely) and **replace every mock data source with a real API call to the backend**, while wiring `VideoAnalysisPage` to your actual detection pipeline instead of a random-number generator.

## 3. Architecture change: from single-file mock to real app

### 3.1 Current (Meridian as delivered)
```
Browser
  └─ ref.html (one file)
       ├─ React/ReactDOM/htm/Chart.js loaded from CDN <script> tags
       ├─ ~40 components, all in one <script> block
       └─ All data from in-file JS constants + seeded RNG
       (no network calls of any kind)
```

### 3.2 Target
```
Browser (web/, Vite + TypeScript build)
  └─ Same visual design, componentized into web/src/ (per AGENT_BUILD_SPEC_v2 §2 layout)
       ├─ api/client.ts   — typed fetch wrapper, one function per SDD v1 §8 endpoint
       ├─ ws/client.ts    — WebSocket client for live alerts/health
       └─ pages/*         — same 11 pages, now reading from React Query + the API, not local constants
                │
                ▼  HTTPS + WSS
FastAPI backend (backend/, per SDD v1 §5–§8)
                │
                ▼
Worker processes (worker/, per SDD v1 §6) ── YOUR EXISTING PIPELINE ── produces real alerts
```
This is **the same backend architecture already specified in SDD v1** — this plan does not change the backend design, only formalizes that Meridian is now its frontend, and adds one new capability: **on-demand file analysis** (§5), which v1 didn't need because v1 assumed only live RTSP cameras.

### 3.3 Why the CDN/no-build approach must be replaced
- No TypeScript checking → the exact class of bug you hit (mismatched field names between UI and backend) is invisible until runtime.
- No code splitting → 3,697 lines in one file becomes unmaintainable as real logic is added.
- No environment config → API base URL, WebSocket URL, and auth can't be safely parameterized per deployment.
- CDN dependency at runtime → app breaks offline or if a CDN is blocked (already observed in this sandbox).

Migration is mechanical, not a rewrite: each `function X() { ... }` in the current file becomes `web/src/pages/X.tsx` or `web/src/components/X.tsx` with the same JSX logic, translated from `htm` template-tag calls to real JSX (see AGENT_BUILD_SPEC_v2 §3 for the exact translation pattern).

## 5. Priority fix: real Video Analysis (this is what you reported broken)

### 5.1 Current broken behavior
`VideoAnalysisPage` lets you drop a video file, plays it in an HTML `<video>` element, and every ~N frames calls `spawnDetection(frameNum)`, which does:
```js
const type = pick(INCIDENT_TYPES);          // random category, ignores video content
const confidence = Math.round(rand(58, 98)); // random number
```
So alerts (or lack of them) are **statistically random**, never a function of what's in the frame. This matches your earlier report exactly: it "doesn't give alerts for a crime video" — because it was never looking at the video. It also explains why it sometimes *did* show alerts on unrelated content: same reason, random chance.

### 5.2 Target behavior
1. User drops a file → frontend `POST`s it to the backend (**[NEW]** endpoint, see §5.3), not just played locally.
2. Backend runs the **same worker pipeline** (SDD v1 §6.1 cascade) against the uploaded file instead of a live RTSP stream — this reuses `core/cascade.py`, `core/tracking.py`, `core/risk/engine.py` unchanged; only the ingest source differs (file instead of RTSP, per SDD v1 `ING-01`, which already lists "local file" as a supported source).
3. Because this file has **no configured zones** (it's an ad-hoc upload, not a fixed installed camera), the analysis runs in a **reduced-requirement mode**: zone-dependent signals (`ZONE_ENTER`, `ZONE_DWELL`) are skipped; only zone-independent signals apply (`LOITER`, `RUNNING`, `UNATTENDED`). This is an honest capability limit, not a workaround — say this in the UI (§5.4).
4. Frontend polls or subscribes (WS) for progress and real detections as the backend processes the file, and renders the **real** bounding boxes, risk scores, and any real alerts on the timeline — replacing `spawnDetection` entirely.
5. If zero alerts fire, the UI must say why (score/threshold reached vs. not), not silently show nothing — this directly addresses your repeated "it doesn't give alerts" reports, which were as much a **feedback/legibility problem** as a detection problem.

### 5.3 New endpoints required
| Method | Path | Purpose |
|---|---|---|
| POST | `/analysis/upload` | Multipart upload; returns `{job_id}` |
| GET | `/analysis/{job_id}/status` | `{status: queued\|processing\|done\|error, progress_pct, frames_done, frames_total}` |
| GET | `/analysis/{job_id}/result` | Final detections, risk timeline, any alerts raised (same alert schema as SDD v1 §7.2) |
| WS | `/analysis/{job_id}/stream` | Live per-frame detections + running risk score while processing (drives the live overlay, replacing the fake `box`/`liveConfidence` state) |

Backend behavior: a dedicated `analysis_worker` (short-lived, one process per upload, not a persistent per-camera worker) runs the file through the cascade + tracker + risk engine, using either **no zones** or **zones the user draws on a extracted frame before running** (better — see §5.4 UX).

### 5.4 UX fix, not just a data fix
Add a **required step** before "Analyze" is clickable: show one extracted frame from the upload and let the user draw at least one zone (reuse the `ZoneEditor`/`ZoneCanvas` component that already exists for the Camera pages — do not build a second polygon editor). If the user skips this, show a persistent banner during and after analysis: *"No zone was drawn — zone-based signals (restricted-area entry, dwelling) are disabled for this run. Loitering, running, and abandoned-object signals still apply."* This directly targets the exact misunderstanding this conversation surfaced: **the pipeline needs a configured scene, not an arbitrary clip**, and the UI must say so instead of silently returning nothing.

Also show, always, even with zero alerts: the **live risk score per detected person**, updating in real time (this is what `Gauge`/`Sparkline`/`ConfidenceBar` components already exist for) — so "it did something, just didn't cross threshold" is visibly different from "it saw nothing." This one change resolves most of the "doesn't give alerts" confusion class by itself.

## 7. What does NOT change

- The detection/tracking/risk model itself (SDD v1 §6) — unchanged. Meridian's `RISK_ENGINE_DEFAULTS` already matches it exactly, confirming the frontend was designed against the same spec.
- RBAC roles and permissions (SDD v1 §2) — Meridian's `ROLES`/`PERMISSIONS` already match; reuse verbatim as the frontend's permission table, driven by the real `/me` endpoint instead of a hardcoded role variable.
- Security/privacy/retention requirements (SDD v1 §10) — unchanged, now enforced for real once real data flows.
- Evaluation protocol (SDD v1 §12.2) — unchanged; the Video Analysis feature in §5 is a good source of **staged test clips** for that protocol, not a replacement for it.

## 9. Acceptance check for "no more fake alerts"

Before calling this done, verify:
- [ ] `grep -r "seededRandom\|Math.random\|pick(" web/src` returns **nothing**.
- [ ] Uploading a video with no motion and no zone produces **zero** alerts and an explicit on-screen reason, not silence.
- [ ] Uploading a staged clip (bag left + walk away) produces a real `UNATTENDED` alert with a real clip, matching SDD v1 §6.10.
- [ ] Killing the backend makes the UI show a connection error, not frozen-but-plausible fake data (a risk with any mock system is that it fails silently into looking fine).
